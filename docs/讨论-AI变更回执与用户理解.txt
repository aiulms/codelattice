你说得对：这里不应该先约束开发 AI，而应该做一个 UI-first 的“项目理解层”。

最合适的方案不是单纯让大模型读仓库后写一篇介绍，也不是直接把代码图展示给用户，而是：

> CodeLattice 提供可验证的事实，大模型负责把事实翻译成人能理解的产品故事，WebUI 负责交互式呈现。

## 为什么不能只靠大模型阐述

让大模型直接读取仓库并生成说明，会有几个问题：

- 容易把推断说成事实。
- 每次生成的项目结构可能不同。
- 大仓库无法一次完整放进上下文。
- 最终往往又变成长篇文字，用户依然看不进去。
- 文字和实际代码之间缺少可点击、可验证的连接。

但只展示现有代码图也不够。普通用户看到 crate、module、symbol、CALLS edge，仍然不知道“这个项目到底是干什么的”。

因此需要在代码图上面增加一层“产品语义图”。

## 从代码图升级为产品理解图

CodeLattice 当前拥有的是：

```text
文件 → 符号 → 调用 → 依赖 → 影响
```

用户真正想看到的是：

```text
项目 → 功能 → 使用场景 → 核心流程 → 数据 → 外部系统 → 风险与限制
```

大模型的主要任务，是把底层代码证据聚合成上层概念：

- 哪些入口共同组成“用户登录”功能。
- 哪些模块共同实现“代码分析”能力。
- 一个请求从界面进入后经过哪些关键步骤。
- 项目会读取、保存或发送哪些数据。
- 哪些功能只是实验性实现。
- 哪些结论无法从静态代码确认。

这些产品节点都必须能够向下展开，最终落到真实文件、符号和调用边。

## WebUI 应该是什么样

我建议首页不再首先展示一张巨大的技术图，而是提供四个入口。

### 1. 这个项目是什么

生成一张简洁的项目卡片：

- 项目解决什么问题。
- 面向哪些使用者。
- 提供哪些主要能力。
- 如何启动和使用。
- 当前成熟度和主要限制。
- CodeLattice 对这些结论的置信度。

用户可以选择“小白、产品、开发者”三个解释层级，底层证据相同，只改变表达方式。

### 2. 功能地图

把现有图组件降级为可复用的局部组件，默认展示产品功能，而不是所有代码节点：

```text
代码分析
├── 项目发现
├── 符号提取
├── 调用解析
├── 缓存与增量分析
├── MCP 服务
└── Web 工作台
```

点击“缓存与增量分析”后，再逐层展开：

```text
产品能力 → 核心流程 → 模块 → 文件 → 符号
```

这样用户从“它能做什么”进入“它是怎么实现的”，而不是一上来掉进几万个节点里。

### 3. 核心流程讲解

将现有调用图封装成“流程播放器”。

例如用户点击“分析一个项目”，页面按步骤展示：

1. 发现项目和语言。
2. 提取文件与符号。
3. 解析 imports 和 calls。
4. 组装图谱。
5. 写入缓存。
6. 返回 MCP/WebUI 结果。

每一步包含：

- 一句人话说明。
- 涉及的模块。
- 输入和输出。
- 可点击的局部关系图。
- 代码证据。
- “这里无法确认”的内容。

这会比静态大图更容易理解。

### 4. 和项目对话

大模型不能只返回文字。用户问：

> “缓存为什么会占这么多内存？”

回答页面应该同时完成三件事：

- 给出自然语言解释。
- 自动切换到相关功能和流程。
- 在图上高亮 `CacheEntry`、`GraphView`、persistent cache 等证据节点。

也就是：

> 对话负责导航，图负责建立空间认知，源码负责验证。

## 可以组件化的 WebUI 能力

现有图组件可以拆成以下通用组件：

- `GraphCanvas`：基础布局、缩放、选择。
- `FeatureMap`：产品功能关系。
- `FlowPlayer`：按步骤播放调用或数据流。
- `EvidenceDrawer`：展示文件、符号和代码证据。
- `NarrativePanel`：大模型讲解。
- `ConfidenceBadge`：事实、推断、未知。
- `ChangeOverlay`：显示两个版本之间功能和流程的变化。
- `MiniGraph`：嵌入项目介绍、问答和功能详情页的小型关系图。

这样“图”不再是一个独立页面，而是整个项目理解体验中的基础 UI 组件。

## 推荐的生成流程

```mermaid
flowchart LR
    A["CodeLattice 代码图"] --> B["确定性证据包"]
    B --> C["大模型产品语义归纳"]
    C --> D["结构化理解模型"]
    D --> E["项目首页"]
    D --> F["功能地图"]
    D --> G["流程播放器"]
    D --> H["可视化问答"]
    E --> I["文件与符号证据"]
    F --> I
    G --> I
    H --> I
```

关键点是大模型不能直接输出最终网页，而是输出结构化数据，例如：

```json
{
  "capability": "增量缓存",
  "summary": "避免对未变化项目重复分析",
  "confidence": "high",
  "entryPoints": [],
  "coreFlow": [],
  "evidenceNodeIds": [],
  "unknowns": []
}
```

WebUI 再根据这个模型渲染。这样结果稳定、可缓存、可点击，也可以更换大模型。

## 最合适的 P0

第一版不需要覆盖所有理解场景，可以只做：

1. 项目一句话说明和能力列表。
2. 可下钻的功能地图。
3. 三到五条核心流程播放器。
4. 带图谱联动和证据引用的项目问答。
5. “事实／推断／未知”标记。

并用一个非常直接的标准验收：

> 一个从未看过项目的人，能否在五分钟内回答：项目做什么、有哪些核心功能、一项功能如何运行、数据去了哪里、目前哪里最不确定？

这才是真正的“用户理解项目”，而不是生成另一份没人阅读的架构文档。

所以我的结论是：应该借助大模型，但大模型只负责语义归纳、解释和导航；CodeLattice 图谱负责事实和证据；WebUI 负责让理解过程可视化、可探索、可验证。这个方向可以命名为 `Project Understanding`，并作为 WebUI 的新主入口。
